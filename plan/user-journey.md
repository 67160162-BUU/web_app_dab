# User Journey — DAB DETECTOR
### เว็บเกมตรวจจับท่า Dab ด้วย Computer Vision พร้อมระบบให้คะแนนและจัดอันดับ

> เอกสารนี้จัดทำตามโครงสร้างในเอกสาร "จาก User Journey สู่โค้ดจริงด้วย AI"
> ใช้เป็นแหล่งข้อมูลสำหรับกรอก Prompt Template (หัวข้อ 7) และออกแบบฐานข้อมูล (หัวข้อ 8)

---

## 1. ภาพรวมระบบ

**ชื่อระบบ:** Dab Detector — The Dab Challenge

**หมวดอุตสาหกรรม:** Web-based Fitness Game / Interactive Entertainment

**คำอธิบายสั้น:**
เว็บแอปที่เปิดกล้องผู้ใช้ แล้วใช้ AI ตรวจจับโครงร่างร่างกาย (Pose Estimation) เพื่อวัดว่าผู้ใช้ทำท่า "Dab" ได้ถูกต้องและเร็วแค่ไหนภายในเวลา 20 วินาที ระบบให้คะแนนตามความแม่นยำของท่า และบันทึกคะแนนขึ้นกระดานจัดอันดับระดับโลก

**สิ่งที่ทำให้ระบบนี้ต่างจากโปรเจกต์กลุ่มอื่น:**
ระบบส่วนใหญ่รับ input จากการพิมพ์/คลิก แต่ระบบนี้รับ input จาก **การเคลื่อนไหวร่างกายจริงผ่านกล้อง** จึงมี Edge Case เฉพาะตัวที่ระบบทั่วไปไม่มี เช่น ผู้ใช้ไม่อนุญาตกล้อง, แสงไม่พอ, ยืนไม่เต็มเฟรม ซึ่งเป็นจุดที่ต้องออกแบบ UX ให้ดีเป็นพิเศษ

## 2. Tech Stack และเหตุผล

Stack หลักยึดตามที่อาจารย์กำหนดทุกประการ และเพิ่มไลบรารีฝั่ง client เข้ามา 1 ตัวคือ MediaPipe

| ชั้นระบบ (Layer) | เครื่องมือที่ใช้ | เหตุผลที่เหมาะกับระบบนี้ |
|---|---|---|
| **Frontend** | HTML + CSS + JavaScript ธรรมดา (ไม่มี framework) | ไม่มี build step ทำให้แก้ไฟล์แล้วเห็นผลทันทีผ่าน volume mount ของ Docker และ MediaPipe โหลดผ่าน CDN ได้โดยตรงด้วย ES Module ไม่ต้องมี bundler |
| **AI / Pose Detection** | Google MediaPipe Pose Landmarker (`@mediapipe/tasks-vision` ผ่าน CDN) | **รันบนเครื่องผู้ใช้ทั้งหมด (on-device)** ภาพจากกล้องไม่ถูกส่งขึ้น server เลย ทำให้สอดคล้องกับ PDPA โดยธรรมชาติ, ไม่ต้องเทรนโมเดลเอง, ไม่กิน bandwidth/CPU ของ server และไม่มีค่าใช้จ่าย API |
| **Backend** | FastAPI (Python) | ตรงกับที่อาจารย์สอน, ทำหน้าที่ 2 อย่างคือ serve ไฟล์ frontend เป็น static files และเปิด REST API สำหรับ leaderboard, มี Swagger UI ที่ `/docs` ให้ทดสอบ API ได้ทันที |
| **ฐานข้อมูล** | PostgreSQL (container ผ่าน Docker Compose) | เก็บเฉพาะคะแนนและชื่อเล่น ไม่เก็บภาพหรือข้อมูลชีวมิติใดๆ ทำให้ schema เล็กและปลอดภัย |
| **ORM** | SQLModel | syntax คล้าย Pydantic ที่ FastAPI ใช้อยู่แล้ว เรียนรู้เพิ่มน้อย และป้องกัน SQL Injection ให้โดยอัตโนมัติ |
| **การจัดการรันระบบ** | Docker + Docker Compose | `docker compose up` คำสั่งเดียวได้ครบทั้งระบบ ทุกเครื่องในกลุ่มได้ผลเหมือนกัน |
| **Version Control** | Git + GitHub | 1 repo ต่อกลุ่ม, branch `feature/*` แล้วส่ง Pull Request |
| **Deploy** | Render หรือ Railway (ประเภท Docker) | อ่าน Dockerfile ตัวเดียวกับตอน dev, **ต้องได้ HTTPS** ซึ่งเป็นเงื่อนไขบังคับของระบบนี้ (ดูข้อควรระวังด้านล่าง) |

### ⚠️ ข้อจำกัดทางเทคนิคที่ต้องรู้ตั้งแต่วันแรก

1. **`getUserMedia()` ทำงานเฉพาะบน HTTPS หรือ `localhost` เท่านั้น**
   → ตอน dev เข้าผ่าน `http://localhost:8000` ได้ปกติ แต่ถ้าเปิดผ่าน IP ในวง LAN (เช่น `http://192.168.1.5:8000`) กล้องจะไม่ทำงาน
   → ตอน deploy ต้องเลือกบริการที่ให้ HTTPS ฟรี (Render และ Railway ให้อยู่แล้ว)

2. **ภาพจากกล้องเป็นภาพกระจก (mirror)**
   → ต้องใส่ `transform: scaleX(-1)` ที่ทั้ง `<video>` และ `<canvas>`
   → และต้องจำไว้ว่า landmark ที่ MediaPipe เรียกว่า "left" จะปรากฏอยู่ทางขวาของภาพที่ผู้ใช้เห็น

3. **โมเดลมีขนาดไฟล์ ต้องมีหน้า loading**
   → `pose_landmarker_lite` ประมาณ 3 MB + WASM runtime อีกส่วนหนึ่ง โหลดครั้งแรกใช้เวลา 2–5 วินาที ห้ามปล่อยหน้าจอว่างเปล่า

4. **Safari บน iOS ต้องใส่ `playsinline` ที่ `<video>`** ไม่งั้นวิดีโอจะเด้งเป็น fullscreen ทับ UI ทั้งหมด

## 3. Persona

**ชื่อ:** "บิว"

**อายุ:** 20 ปี

**อาชีพ:** นักศึกษาปี 2

**พฤติกรรม:**
เล่น TikTok และดู Twitch เป็นประจำ ชอบเกมที่เล่นจบใน 1 นาทีและแชร์ผลให้เพื่อนดูได้ทันที ไม่ชอบสมัครสมาชิกหรือกรอกฟอร์มยาวๆ ใช้โน้ตบุ๊กเป็นหลัก บางครั้งเปิดจากมือถือ

**สถานการณ์:**
เพื่อนส่งลิงก์มาในกลุ่มไลน์พร้อมข้อความว่า "กูได้ 12 มึงลองสิ" บิวเปิดลิงก์จากมือถือระหว่างนั่งรอเรียน มีเวลาว่างประมาณ 3 นาที

**เป้าหมายของผู้ใช้:**
เข้าเว็บแล้วได้เล่นทันทีภายในไม่เกิน 30 วินาที รู้คะแนนตัวเอง เทียบกับเพื่อนได้ และแชร์กลับเข้ากลุ่มได้

**Pain Point ที่ต้องแก้:**
- กลัวว่าเว็บจะแอบอัดวิดีโอตัวเอง → ต้องบอกให้ชัดก่อนขออนุญาตกล้อง
- ไม่รู้ว่าท่า Dab ที่ถูกต้องคือท่าไหน → ต้องมีภาพตัวอย่าง
- ถ้ากดแล้วไม่มีอะไรเกิดขึ้นจะปิดทิ้งทันที → ทุกสถานะต้องมี feedback

## 4. ตาราง User Journey

| # | ขั้นตอน | สิ่งที่ผู้ใช้ทำ | สิ่งที่ระบบทำ | ไฟล์ที่เกี่ยวข้อง |
|---|---|---|---|---|
| 1 | **หน้าแรก** | เปิดลิงก์ เห็นชื่อเกมและปุ่มเดียว "เริ่ม DAB" พร้อม GIF ตัวอย่างท่าที่ถูกต้อง | แสดง landing page, เริ่มโหลดโมเดล MediaPipe เบื้องหลังทันที (preload) | `index.html` |
| 2 | **ขออนุญาตกล้อง** | อ่านข้อความ "ภาพจะไม่ถูกบันทึกหรือส่งออกจากเครื่อง" แล้วกดปุ่ม → เบราว์เซอร์เด้งขออนุญาต → กด Allow | เรียก `getUserMedia()` **หลังจากผู้ใช้กดปุ่มแล้วเท่านั้น** ไม่ขอทันทีตอนโหลดหน้า | `pages/camera-setup.html` |
| 3 | **ตั้งท่า (Calibration)** | ยืนถอยหลังให้ตัวเองอยู่ในกรอบเงาที่แสดงบนจอ | ตรวจว่าเห็น landmark ไหล่ 2 ข้างและสะโพก 2 ข้างชัดเจน (visibility > 0.7) ถ้าครบให้ขึ้น "พร้อม!" อัตโนมัติ พร้อมเก็บค่า `shoulderWidth` ไว้เป็นฐานคำนวณ | `pages/camera-setup.html`, `js/pose.js` |
| 4 | **นับถอยหลัง** | มองจอ รอ 3-2-1 | นับถอยหลังพร้อมเสียง แล้วเริ่มจับเวลา 20 วินาที | `js/game.js` |
| 5 | **เล่นเกม** | ทำท่า Dab สลับซ้าย-ขวาให้เร็วและถูกต้องที่สุด | ตรวจทุกเฟรม (~30 fps): คำนวณคะแนนท่า, วาดโครงกระดูกทับภาพและเปลี่ยนสีตามคะแนน, นับจำนวนครั้ง, แสดงเวลาที่เหลือ | `js/game.js`, `js/dab.js` |
| 6 | **ดูผล** | เห็นคะแนนรวม + คะแนนแยกรายเกณฑ์ + ภาพนิ่งช็อตที่ทำได้ดีที่สุด | หยุดกล้อง, คำนวณคะแนนสุดท้าย, capture frame ที่คะแนนสูงสุดจาก canvas | `pages/result.html` |
| 7 | **บันทึกคะแนน** | กรอกชื่อเล่น (ไม่เกิน 12 ตัวอักษร) แล้วกด "ส่งคะแนน" — หรือกดข้ามได้ | `POST /api/scores` ส่งเฉพาะ `{nickname, score, dab_count, mode}` **ไม่ส่งภาพ** | `js/api.js`, `routers/scores.py` |
| 8 | **ดูกระดานอันดับ** | เห็น Top 20 และตำแหน่งของตัวเองไฮไลต์ไว้ | `GET /api/scores/top?limit=20` | `pages/leaderboard.html` |
| 9 | **เล่นซ้ำ / แชร์** | กด "เล่นอีก" (กลับไปข้อ 4 โดยไม่ต้องขออนุญาตกล้องใหม่) หรือกด "แชร์" | คงสถานะกล้องไว้, สร้างภาพผลคะแนนสำหรับดาวน์โหลด/แชร์ | `pages/result.html` |

> **หมายเหตุตามหัวข้อ 3 ของเอกสารอาจารย์:** ชื่อไฟล์ใน `frontend/pages/` ตั้งตามชื่อขั้นตอนใน journey โดยตรง เพื่อให้ prompt AI และตรวจงานง่าย

## 5. Edge Cases

จัดลำดับตามความสำคัญ — กรณีที่ 1–3 คือกรณีที่ต้องทำให้ได้ในสัปดาห์แรก

| # | สถานการณ์ | ระบบต้องทำอะไร |
|---|---|---|
| 1 | **ผู้ใช้กด "Block" ไม่อนุญาตกล้อง** | แสดงหน้าอธิบายว่าเกมนี้จำเป็นต้องใช้กล้อง พร้อมวิธีเปิดสิทธิ์ใหม่ในเบราว์เซอร์ (มีภาพประกอบ) และมีปุ่ม "ลองใหม่" — **ห้ามปล่อยจอขาว** |
| 2 | **เครื่องไม่มีกล้อง หรือกล้องถูกโปรแกรมอื่นใช้อยู่** | จับ error จาก `getUserMedia()` แยกประเภท (`NotFoundError` / `NotReadableError`) แล้วแสดงข้อความต่างกัน พร้อมเสนอ "โหมดดูอันดับอย่างเดียว" |
| 3 | **แสงน้อยเกินไป / ยืนไม่เต็มเฟรม** | ถ้า visibility ของ landmark หลักต่ำกว่าเกณฑ์ติดต่อกันเกิน 1 วินาที แสดงคำเตือน "ขยับให้เห็นตัวมากขึ้น" หรือ "แสงน้อยเกินไป" **ไม่ให้เริ่มเกมจนกว่าจะผ่าน** |
| 4 | **มีคนเดินผ่านหลังจอ / มีคนมากกว่า 1 คนในเฟรม** | ตั้ง `numPoses: 1` และให้ MediaPipe จับคนที่เด่นที่สุด แสดงข้อความ "ตรวจพบมากกว่า 1 คน — คะแนนอาจคลาดเคลื่อน" |
| 5 | **ผู้ใช้ค้างท่า Dab ไว้เฉยๆ เพื่อโกงคะแนน** | ใช้ state machine: ต้องกลับสู่ท่าปกติ (คะแนน < 40) ก่อนถึงจะนับครั้งถัดไปได้ ค้างท่าไว้จะได้แค่ 1 ครั้ง |
| 6 | **ผู้ใช้ถือรูปภาพคนทำท่า Dab มาส่องกล้อง** | ตรวจว่ามีการเคลื่อนไหวจริงระหว่างเฟรม ถ้า landmark นิ่งสนิทเกินไปให้ไม่นับคะแนน |
| 7 | **ผู้ใช้ปิดแท็บ / สลับแอปกลางเกม** | ดักอีเวนต์ `visibilitychange` แล้ว pause เกม เมื่อกลับมาให้เริ่มรอบใหม่ ไม่ให้นับต่อจากเดิม |
| 8 | **ชื่อเล่นซ้ำ / ว่างเปล่า / มีคำหยาบ** | ถ้าว่างให้ใช้ "Anonymous" อัตโนมัติ, จำกัด 12 ตัวอักษร, กรองคำต้องห้ามพื้นฐานฝั่ง backend ด้วย (ไม่เชื่อ frontend อย่างเดียว) |
| 9 | **มีคนยิง API ส่งคะแนนปลอมโดยตรง** | backend validate ว่า `score` อยู่ในช่วง 0–100 และ `dab_count` ไม่เกินค่าที่เป็นไปได้ใน 20 วินาที (เช่น ≤ 40 ครั้ง) ถ้าเกินให้ปฏิเสธด้วย HTTP 422 |
| 10 | **เครื่องช้า เฟรมเรตตก** | ถ้า fps ต่ำกว่า 15 ติดต่อกัน ให้ลดความละเอียดวิดีโอลงอัตโนมัติ และแสดงคำเตือน |
| 11 | **ยังไม่มีใครส่งคะแนนเลย (leaderboard ว่าง)** | แสดงข้อความ "ยังไม่มีใครกล้า — เป็นคนแรกเลยไหม?" พร้อมปุ่มเริ่มเกม ไม่แสดงตารางเปล่า |

## 6. Acceptance Criteria

เกณฑ์ที่โค้ดต้องผ่าน ใช้สำหรับวางใน Prompt Template และใช้ตรวจงานเอง

**ด้านการใช้งาน**
- [ ] จากหน้าแรกถึงเริ่มเล่นได้ใช้เวลาไม่เกิน 30 วินาที และกดไม่เกิน 3 ครั้ง
- [ ] ทุกสถานะที่ต้องรอ (โหลดโมเดล, เปิดกล้อง) มีตัวบ่งชี้ให้ผู้ใช้เห็น ไม่มีจอว่างเปล่าเกิน 1 วินาที
- [ ] ข้อความแจ้งว่าไม่มีการบันทึกภาพต้องแสดง**ก่อน**ที่เบราว์เซอร์จะขออนุญาตกล้อง

**ด้านการตรวจจับ**
- [ ] ทำท่า Dab ถูกต้องแล้วต้องได้คะแนนเกิน 75 คะแนน
- [ ] ยกแขนขึ้นเฉยๆ ทั้งสองข้าง หรือชูมือ ต้องได้คะแนนต่ำกว่า 40 คะแนน (ไม่ใช่ false positive)
- [ ] ตรวจจับได้ทั้ง Dab ซ้ายและ Dab ขวา
- [ ] คะแนนต้องไม่เปลี่ยนตามระยะห่างจากกล้อง (ยืนใกล้/ไกลแล้วทำท่าเดิม คะแนนต่างกันไม่เกิน 10 คะแนน)
- [ ] คะแนนบนจอต้องไม่กระพริบไปมา (ใช้ค่าเฉลี่ยย้อนหลัง 5 เฟรม)

**ด้านเทคนิค**
- [ ] `docker compose up` แล้วเข้า `http://localhost:8000` เห็นหน้าเว็บ และ `/docs` เห็น Swagger UI
- [ ] ไม่มี request ใดที่ส่งข้อมูลภาพหรือวิดีโอออกจากเบราว์เซอร์ (ตรวจได้จากแท็บ Network)
- [ ] ใช้งานได้บนมือถือ (responsive) และหน้าจอไม่หมุน/เด้ง fullscreen บน iOS
- [ ] คะแนนที่ส่งขึ้น API ปรากฏใน leaderboard ทันทีเมื่อ refresh

## 7. Data Model เบื้องต้น (สำหรับสัปดาห์ที่ 2)

ทำตามวิธีในหัวข้อ 8 ของเอกสารอาจารย์ — ขีดเส้นใต้คำนามใน User Journey จะได้ Entity ดังนี้

**คำนามที่พบ:** ผู้เล่น, คะแนน, รอบการเล่น, โหมดเกม, อันดับ

เนื่องจากระบบนี้ไม่มีการล็อกอิน Entity จึงเหลือเพียงตารางเดียวในช่วงแรก

```
Score
├── id            : int, PK
├── nickname      : str, ≤ 12 ตัวอักษร
├── score         : float, 0–100
├── dab_count     : int
├── mode          : str  ("rush" | "perfect" | "hold")
└── created_at    : datetime
```

**เหตุผลที่ไม่มีตาราง User:** journey ระบุชัดว่าผู้ใช้ไม่ต้องสมัครสมาชิก การเพิ่มตาราง User จะขัดกับ Pain Point ของ Persona
**แนวทางขยายในสัปดาห์ที่ 4:** ถ้าจะเพิ่มระบบล็อกอิน ให้เพิ่มตาราง `User` แล้วให้ `Score.user_id` เป็น nullable foreign key เพื่อให้คนที่ไม่ล็อกอินยังเล่นได้เหมือนเดิม (one-to-many)

**API ที่ต้องมี**

| Method | Endpoint | หน้าที่ | ขั้นตอนใน journey |
|---|---|---|---|
| `POST` | `/api/scores` | บันทึกคะแนน | ข้อ 7 |
| `GET` | `/api/scores/top?limit=20` | ดึงอันดับสูงสุด | ข้อ 8 |
| `GET` | `/api/scores/rank/{score}` | หาว่าคะแนนนี้อยู่อันดับที่เท่าไร | ข้อ 6 |

**หลักการสำคัญ:** ค่าระยะทางทุกค่าต้องหารด้วยความกว้างไหล่ (`dist(11, 12)`) ก่อนเสมอ เพื่อให้ผลลัพธ์ไม่เปลี่ยนตามระยะห่างจากกล้องและขนาดตัวของแต่ละคน

**เกณฑ์การให้คะแนนท่า Dab (5 องค์ประกอบ)**

| องค์ประกอบ | ความหมาย | น้ำหนัก |
|---|---|---|
| `straight` | แขนข้างที่เหยียด — มุมข้อศอกควรมากกว่า 160° | 25% |
| `raised` | ปลายมือของแขนที่เหยียดต้องสูงกว่าไหล่ | 15% |
| `bend` | แขนอีกข้างพับ — มุมข้อศอกประมาณ 30–70° | 20% |
| `tuck` | ข้อมือของแขนที่พับต้องอยู่ใกล้จมูก | 25% |
| `align` | แขนท่อนบนทั้งสองข้างต้องเรียงเป็นเส้นเฉียงเดียวกัน | 15% |

ใช้ฟังก์ชันแบบไล่ระดับ (smoothstep) แทนการตัดสินแบบผ่าน/ไม่ผ่าน เพื่อให้บอกผู้ใช้ได้ว่า "แขนยังเหยียดไม่ตรงพอ" แทนที่จะบอกแค่ว่าไม่ผ่าน
